# Single-file and prefix save units, and reading PSP disc IDs on the Thor

Until now every save unit was a set of folders, each zipped under a fixed root name, all in one parent folder: Azahar's `data/`, Eden's title folder. melonDS and PPSSPP keep their saves in shapes of their own, so a save unit is now one of three kinds, each hashed, packed, backed up and restored as itself through the same journal (ADR 0011), and uploaded as Argosy uploads it, so either app's save restores in the other. Every kind is restored beside the unit, in a folder other games' saves share (Eden's profile folder, melonDS's save folder, PPSSPP's `SAVEDATA`), so a restore another game left unfinished there is undone too, by whichever game is read first.

**DS saves in melonDS: one raw file.** melonDS keeps a game's save as `<the ROM file's name, its last extension replaced by .sav>` in its save folder (`SramProvider.kt`). On the Thor that folder is `ROMs/saves/melonDS`, set in melonDS with Save next to ROM file off, beside Eden's. The save goes up as the file itself, `<ROM>.sav` under emulator `melonds`, as Argosy uploads it; RomM's hash of a raw save is its MD5, and RomM's web player keeps its `.srm` raw under the same id, so that restores as melonDS's too. melonDS makes an empty `.sav` when a game first runs: that is no save and never goes up, but a restore moves it aside like any old save. The installed file's name is the key, so nothing is read or remembered; two installed games whose saves would have one name as the SD card compares names (a DS and a DSi game, say) both stop. DSiWare isn't synced: melonDS runs it from its DSi NAND, which holds its save, and Loom tells it as melonDS does (`RomProcessor`): a game code starting with H or K and the DSiWare category at 0x234. A raw save on RomM must be one melonDS reads as it is: an archive, a DeSmuME save (its footer would be read as part of the save) or an empty file can never be restored. Argosy's 28-byte hardcore trailer comes off before melonDS gets the save, decided as Argosy's own `getTrailerSize` decides it; RomM's hash stays that of the bytes with the trailer, so the baseline holds both hashes and `/downloaded` sends RomM's. A raw save's backup is the file itself, named `.sav`.

**PSP saves in PPSSPP: every folder starting with the disc ID.** PPSSPP names a game's save folders in its memory stick's `PSP/SAVEDATA` after its disc ID (`ULUS10064DATA00`, `ULUS10064SETTINGS`). On the Thor the memory stick is `ROMs/saves/PPSSPP`; the stick, its `PSP` folder or `SAVEDATA` may be the folder chosen, as in Argosy. A game's save is every folder directly in `SAVEDATA` whose name starts with its disc ID, ignoring case, each zipped under its own name, under emulator `ppsspp`: Argosy's and Sigil's layout (Argosy's directory entries don't change RomM's hash). Games install data there too, under the same prefix: a copy of the disc, not progress. It is left out by Argosy's rule exactly, so a save hashes the same on both sides: a `PARAM.SFO` of at most 64 KiB that Loom can read and whose bytes hold neither `SAVEDATA_PARAMS` nor `SAVEDATA_FILE_LIST` (an empty one too) marks installed data; a folder without one, or with one Loom can't read, is a save. As the game may have no folder yet, the unit's place, which its baseline records, is `SAVEDATA/<disc ID>*`. A restore replaces all the game's folders, as Argosy's does: the archive's other folders starting with the ID join the unit; folders the archive lacks are emptied, then removed (Argosy deletes them first, and PPSSPP would list an empty one); another game's folders and installed data in the archive (an older Argosy uploaded it) are skipped; a rollback removes the folders it made. An archive can never be restored when it isn't a zip, holds no folder of this game's, would put a save where the card keeps this game's installed data or installed data where it keeps a save, names folders that differ only in case, or unpacks to more than the cap. PPSSPP Gold, which Argosy uploads as `ppsspp_gold`, keeps the same saves on the same memory stick, so its saves count as PPSSPP's own.

**Disc IDs.** RomM 5.4.0 reports a PSP game's disc ID when Sigil read it at scan time (from an ISO, CSO or CHD): its `save_target` when `save_target_layout` is `folder-prefix`, else its `title_id`, taken only in a disc ID's shape (four capitals, five digits). It has none for a zip, a PSN game's PBP, minis, or a ROM scanned before the server had Sigil, so Loom also reads the ID on the Thor from a few sectors: an ISO's `UMD_DATA.BIN`, as Sigil reads it, checked against `PSP_GAME/PARAM.SFO`'s `DISC_ID`, which is PPSSPP's; a CSO v1 frame by frame through its index, as PPSSPP reads it; a PBP's `PARAM.SFO`. CHD, ZSO and CSO v2 are left to RomM. The ID is remembered with the images' paths, sizes and times and RomM's ID, so a scan doesn't read an image again while they are unchanged. When RomM and the image disagree, the image names two IDs, or neither knows, the owner picks the game's save folders from the disc IDs `SAVEDATA`'s save folders start with, the most recently played first, none another installed game has. The pick stands until RomM or the image names another disc, which asks again. Two installed games with one disc ID both stop; RomM's IDs count before either game is read. The test images are synthetic, written by a Python script using only its standard library, which also gives each one's MD5 and answer.

**Save keys.** What names a game's save in a folder every game's saves share (a Switch title ID, a PSP disc ID) lives in one table, `save_keys`, keyed by emulator and game, with where it came from (the image, RomM or the owner) and a fingerprint of what was looked at. Database version 7 creates it from `switch_titles`, whose rows become Eden's as they were. DS saves need no key.

**What can't sync says so once.** A RomM save that can't be laid out as the unit is (any refusal above, a bare file where Azahar's folders should be, an archive of another Switch title), or that is larger than Loom downloads (256 MB, as an old Argosy's PSP archive holding installed data can be), is one save conflict, `SERVER_UNREADABLE`, never a failure each run, and the Thor's save is backed up only once a download passed these checks. Its reason in Loom's words and the unit it was found for are kept with the conflict (`detail` and `unit_path` in `save_conflicts`, database version 7). The choice offers only Keep Thor and Skip, and while RomM's newest save (its id and hash) and the unit stay the same, no sync downloads it again. A Restore or Keep server that finds it records the same conflict. Likewise, a save larger than Loom would restore for its emulator (64 MB for 3DS, DS and PSP games, 256 MB for Switch games) is unsupported, with its size and the cap, rather than failing each run; for a PSP game, that most likely means data the game installed with an SFO that doesn't say so.

## Considered Options

- melonDS saving next to the ROMs, its default and the first plan: a game melonDS hasn't scanned yet, as any game Loom just installed is, saves in `Android/data` instead, where Loom can't read it, so one game would keep two saves; and `.sav` files would sit in the folders Cocoon indexes.
- Zipping the `.sav`, as every other unit is: Argosy and the web player upload it raw, so neither app's save would restore in the other.
- PPSSPP's own rule for installed data (a folder of 10 MB or more, in its size display): Argosy's rule decides what it uploads, and a different one would hash the same folders differently on each side, which would never be in sync.
- Parsing PARAM.SFO's keys instead of Argosy's search for their bytes: stricter, but it would disagree with Argosy on an odd or damaged SFO, and agreeing with Argosy is what keeps the hashes equal.
- One RomM save per PSP folder: RomM pairs saves on (ROM, slot), and Argosy and Sigil keep all of a game's folders as one save.
- RomM's disc ID alone: there is none for zips, PBPs, minis, or ROMs scanned before the server had Sigil.
- A CHD reader on the Thor: libchdr and its codecs for a few sectors, where RomM reads CHDs itself and the owner's pick covers the rest.
- Refusing saves that carry Argosy's trailer instead of stripping it: a save played in hardcore mode on Argosy would never reach melonDS, and Argosy strips the trailer from its own downloads by the same rule.
