# Receive games sent from RomM by claiming, nudged by our own Socket.IO client

RomM 5.4 lets its owner send a game to a device from the web UI ("Install on device"). It keeps an install request, in Redis, until the device claims it (`POST /api/devices/{id}/installs/claim`, which hands back every request the device holds and hasn't reported) and reports how it went (`done`, `already_installed` or `failed`), which ends it. Claiming is the whole protocol; RomM's `/devices` Socket.IO namespace only nudges a connected device to claim. So Loom claims at start, each time it comes to the front, after pairing again, when RomM answers again after being out of reach, and every 15 minutes in the background (periodic WorkManager work, only while games can come); while Loom is in front it holds the socket open to claim the moment a game is sent, and claims every minute instead while the socket can't connect, which also keeps the Thor shown online in RomM's dialog. The socket is a small Engine.IO 4 / Socket.IO 5 client written on Loom's own OkHttp, with its own HTTP client: the token goes only in the namespace's connect payload, and a proxy answering the WebSocket upgrade with a 502 doesn't make the library say RomM is offline. Each request is queued as X in the library queues a game, by Loom's own per-platform file rules, and reported `done` as soon as the game is in the queue (RomM shows "Added to downloads"); a game whose platform's folder Loom would have to ask about (ADR 0009) waits in the queue for that answer and is reported `done` too. Only a lasting problem is reported `failed`, with Loom's reason; a passing one (RomM out of reach, busy, or failing for now) isn't reported, and the next claim returns the request. RomM refusing the device (a token not bound to one, or the device deleted on its Devices page) stops the claims until Loom pairs again, and device installs switched off on the server stop them until a heartbeat says they're back; nothing loops. Loom declares `remote_install` (which RomM needs before it lists the device) at every start and whenever its switch changes, with a PUT of the whole capability dict, and claims only for the device its token is bound to.

## Considered Options

- **socket.io-client-java**, as Argosy uses: proven against RomM, but built on OkHttp 3 and org.json and unproven on OkHttp 5, for a protocol whose part Loom needs (open, connect with a token, ping and pong, two events, disconnect) is small enough to test fully with MockWebServer.
- **A persistent foreground service** keeping the socket open in the background: games would arrive at once even with Loom closed, for a notification that never goes away and a connection held all day. The periodic claim brings them within 15 minutes, or as soon as Loom opens.
- **Honouring the request's `file_ids`**: RomM picks them by its own rule (game, update and DLC files), so a game sent from RomM would install differently from the same game picked in the library. Loom applies the platform's own file rules either way.
- **Reporting `done` only once the game is installed**: a taken request expires two days after the claim, and a download can wait longer than that (for Wi-Fi, the SD card, Loom being opened, or a folder to be chosen); its later report would find nothing. RomM labels `done` "Added to downloads", which is what Loom knows at that point; how the download ends shows in Loom's queue and notifications.
- **Reporting `failed` for an ambiguous folder**: the owner would answer the folder question and then have to send the game again. It waits in the queue instead, in a state "Pause all" can't release into the default folder.
- **A local ledger of the requests handled**: a claim hands back every request not reported yet, and queueing a game already in the queue is reported `done` without a second job, so handling a request twice is harmless. Accepted edge: a report lost on the way, then the game cancelled in Loom before the next claim, brings the game back once.
- **Reading the device's capabilities and merging Loom's in**: RomM replaces the whole dict on each update, and a read then a write could race. Loom owns its device's dict and sends all of it; should a later RomM write keys of its own there, Loom would have to merge them.
