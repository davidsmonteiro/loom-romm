# Decide save sync from a local baseline

RomM 5.3.1's `POST /api/sync/negotiate` compares a device's save with the slot head through the device's sync row, and that row only exists for the version the device itself last uploaded or downloaded. Whenever another device or the web player uploaded last, there is no row and negotiate falls back to comparing timestamps: it can answer `download` over progress made on the Thor (if the Thor's file is older) or `upload` that RomM then refuses with 409. It also has no tombstones, so a slot deleted on the server comes back as an `upload`. RomM 5.4.0 keeps the hashes a device last synced, but on its sync row for one save version, and every slotted upload makes a new version: whenever another client uploaded last, the Thor still has no row for the head and the same timestamp fallback applies. It does record deletions, and answers `delete`, which Loom only ever turns into a question. Loom therefore keeps its own baseline per slot (its hash of the save unit and the folder it was in, plus the slot head's id, hash and time at the last sync; a save in another folder counts as never synced) and decides with a pure rule, `SyncDecider`. An upload happens only when the server is unchanged since the baseline, and a download only when the Thor's save is unchanged or absent and the newer head came from the same emulator. Identical bytes are adopted as the new baseline. Everything else is a save conflict for the user, and so is any answer from negotiate that differs from Loom's own. Negotiate is still called, because it opens the session RomM counts operations in and it sees heads Loom doesn't know about, but it never decides on its own.

Loom syncs one slot per game, `autosave`: RomM's convention, which Argosy and the web player use too, so a save made on another device reaches the Thor and the Thor's reaches it. RomM pairs saves on (ROM, slot) only and doesn't look at `emulator`, so sharing the slot means its newest save can come from another emulator: an EmulatorJS core in the web player, or another 3DS emulator, whose file Azahar may not even read. Loom never applies such a save on its own; a newer head whose emulator isn't Loom's is a save conflict like any other. Where the web player's core keeps the same saves as Loom's emulator, it uses the same id (`melonds`, `ppsspp`, and `azahar` for 3DS), so its saves count as that emulator's; one Loom can't lay out as the emulator keeps it is a conflict saying so (ADR 0014). PPSSPP Gold's `ppsspp_gold` counts as `ppsspp`. Versions outside every slot are never paired, which is where Keep both parks the Thor's copy.

## Considered Options

- Follow negotiate (the first roadmap plan): loses a save the first time another device uploads while the Thor holds unsynced progress.
- Newest wins: compares the Thor's clock with the server's, and a wrong clock silently picks the older save.
- Trust RomM 5.4.0's hash baselines: they are kept per save version, on the device's sync row, so they only help while the Thor itself synced the slot's newest version; whenever another client uploads last, negotiate falls back to timestamps as 5.3.1 does. Loom sends its hashes (on uploads and on `/downloaded`), which makes RomM's answer a better cross-check, and Loom's rule stays.
- A slot only Loom uses (`loom`): no other emulator's save could ever land on the Thor, but no other client would see the Thor's saves either, which is most of the point of syncing.
- Ignore the emulator, as RomM does: `PULL_SAVES` or a restore would put a save from another emulator in place of Azahar's like any newer save.
- Filter negotiate by emulator (RomM 5.4.0's `emulators`): RomM then takes the slot head from Loom's emulators' saves only, so another emulator's newer save would never reach Loom's check, while uploads are still refused with 409 for it, and deletions are kept per slot, not per emulator. Loom doesn't send it.
