# Read Switch title IDs on the Thor with the owner's header key

Eden keeps a Switch game's save in a folder named after its title ID, so Loom can't sync a save without it, and RomM can't supply it: 5.3.1 and 5.4.0 identify Switch images with sigil but call it without keys, so it stops at the encrypted NCA headers and reports that it needs a key. Loom therefore reads the ID on the Thor. An XCI's partition tables (or an NSP's) are plain; each NCA's first 0xC00 bytes are AES-128-XTS encrypted with the console's `header_key`, which the owner already has in the `prod.keys` dumped from their own Switch, kept on the card. Loom reads that one key from `ROMs/prod.keys` (or the Switch folder's), only when a game's title ID isn't known yet, decrypts the first 0x400 bytes of each NCA (a few kilobytes per game, through its own XTS over AES/ECB, as the JCE has none), takes the program ID of the application's program NCA, and wipes the key. The key is never logged, stored, put in an error message or uploaded; the title ID is remembered with the image's path, size and time, so the image isn't read again until it changes. Without a usable key, or for an image Loom can't read, the owner picks the game's save folder from Eden's (once; the answer is remembered and can be changed). The reader is tested against synthetic images encrypted by an independent implementation (Python's `cryptography`) with a made-up key, and against IEEE 1619's XTS vectors: no console's key or game is in the repository.

## Considered Options

- Ask the owner for every game's save folder: no key on the device at all, but a question per game, and a wrong pick syncs another game's save under this one. It stays as the fallback.
- Wait for RomM to report the title ID: it would need the keys on the server, which the owner didn't choose, and no released RomM reads them.
- sigil (the library RomM and Argosy use) through JNI: a native library and its build for one header field, still needing the same key on the device.
- A title database matching file names to title IDs: a large download to keep current, and dump names don't reliably match.
